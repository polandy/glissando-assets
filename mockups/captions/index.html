Editor: Bildtitel

Ein Bild antippen, dann „Bearbeiten“ (Desktop: Doppelklick): unter der Bewegung steht das Feld „Bildtitel“, die Vorschau zeigt ihn sofort. „Abspielen“ startet den Player; antippen blendet die Bedienelemente ein. Drei Bilder haben schon einen Titel. Die Entscheidungsvorschläge zu Speicherung und Darstellung stehen unter „Konzept“.

So funktioniert es

  • Bearbeiten: im Bildeditor unter „Ken Burns“ der Abschnitt „Bildtitel“, ein einzeiliges Feld mit höchstens 80 Zeichen. Gespeichert wird beim Tippen, wie jede Bearbeitung. Leer heißt kein Titel; nichts wird vorbelegt. Das × leert das Feld, Enter schließt die Eingabe.
  • Vorschau: die 16:9-Vorschau im Editor zeigt den Titel so, wie der Player ihn zeigt, nur kleiner.
  • Diashow: die Infotafel zählt „3 von 8“ unter „Bildtitel“. Die Kacheln bleiben ohne Zeichen, sie tragen schon Nummer und Bewegung.
  • Player: unten links über einem leichten Verlauf. Die Größe folgt der Bildschirmhöhe, so wirkt der Titel auf dem Fernseher wie auf dem Handy. Der Titel gehört zur Folie: beim Überblenden blendet er mit, beim Schieben fährt er mit. Die Ken-Burns-Bewegung macht er nicht mit, er steht still.
  • Bedienelemente: sind sie eingeblendet, rückt der Titel über die Zeitleiste hinauf, sonst wäre er verdeckt.
  • Lange Titel umbrechen im Player auf höchstens zwei Zeilen, danach „…“. Das trifft vor allem das Handy im Hochformat.
  • Export und Import: der Titel reist in der .glissando-Datei mit.

Speicherung: Entscheidungsvorschlag

Ein optionales Feld am Bild, an allen drei Stellen gleich benannt. Wie die eigene Bewegung (ADR-0006): fehlt das Feld, gibt es keinen Titel.

Bibliothek       StoredPicture.caption?: string
.glissando-Datei pictures[i].caption      Formatversion 2 → 3
Slideshow-JSON   slides[i].caption        Formatversion bleibt 1
  • Normalisiert an der Grenze: Leerzeichen am Rand weg, Zeilenumbrüche und Tabs werden zu einem Leerzeichen, höchstens 80 Zeichen. Ein leerer Titel wird nicht gespeichert, das Feld fehlt dann. Beim Lesen meldet ein ungültiger Titel den Pfad und den Wert, wie heute.
  • Datei Version 3: eine App mit Version 2 lehnt unbekannte Felder ab. Mit der höheren Version meldet sie „neuere Version“ statt „beschädigt“. Dateien der Versionen 1 und 2 lassen sich weiter importieren.
  • Slideshow-JSON bleibt Version 1: es wird beim Abspielen aus der Bibliothek erzeugt und nirgends gespeichert. Ein optionales Feld kommt dazu, nichts Bestehendes ändert sich.

Kein ADR dafür: es folgt dem Muster von ADR-0006, hier wird nichts abgewogen.

Darstellung im Player: Entscheidungsvorschlag (ADR-0007)

VarianteGewinntKostet
A · Der Titel ist Teil der Folie (Empfehlung)
Text und Verlauf einmal pro Folie mit Canvas 2D gezeichnet, als zweite Textur in den Shader; im DOM-Ersatz ein Element in der Ebene der Folie		Jeder Übergang trägt den Titel mit, ohne Sonderfall: Schieben, Wischen, Kreis. Der spätere Video-Export rendert dieselben Bilder in seiner Auflösung, der Titel ist eingebrannt, ohne zweiten Zeichenweg.Textsatz in eigener Hand: die Schrift muss geladen sein, bevor gezeichnet wird; neu zeichnen bei Größenänderung; eine kleine Textur mehr pro geladener Folie. Für Screenreader liegt der Text zusätzlich unsichtbar im Player.
B · Eine DOM-Ebene über dem Player
für WebGL und DOM-Ersatz gemeinsam, eigene Blende im Takt der Zeitleiste		Scharfer Text vom Browser, CSS statt Textsatz, am wenigsten Code heute.Beim Schieben oder Wischen bleibt der Titel stehen, während das Bild wegfährt. Der Video-Export braucht trotzdem einen Canvas-Zeichenweg, dann gibt es zwei, die gleich aussehen müssen.
C · Text in WebGL mit Glyphenatlas
Signed-Distance-Field-Schrift im Shader		Beliebig skalierbar, eine Textur für alle Titel.Viel Code für eine Zeile Text; Umlaute, Unterschneidung und Umbruch selbst bauen.

Bei A rückt der Titel über die Bedienelemente, indem der Player einen unteren Abstand bekommt (player.captionInset). Der Export kennt keine Bedienelemente und setzt ihn auf 0. Schrift: Instrument Sans 600, schon selbst gehostet.
